## 核心思想：Process over Prompt

Superpowers 不是让 AI 变聪明，而是**强制 AI 遵守软件工程纪律**。你把 AI 当成一个聪明但毛躁的程序员，Superpowers 就是他的开发流程手册。

---

## 14 个子技能，覆盖完整开发流程

```
需求分析 → 设计方案 → 编写计划 → 执行开发 → 测试 → 调试 → 审查 → 收尾
```

### 🧭 入口调度

| 技能 | 做什么 |
|------|--------|
| `using-superpowers` | 每次对话开始时自动加载，确保 AI **先检查有没有适用的 skill，再行动**。防止 AI "直接动手写代码"。 |

### 💡 需求与规划（写代码之前）

| 技能 | 做什么 | 核心铁律 |
|------|--------|---------|
| `brainstorming` | **苏格拉底式提问**，一个一个问清楚需求。探索现有代码、技术栈，给出 2-3 个方案对比。输出设计文档到 `docs/superpowers/specs/`。 | 🚫 **用户批准设计之前，绝不写一行代码。** |
| `writing-plans` | 把设计方案拆成**2-5 分钟能完成的微任务**，每个任务写明具体文件路径、改动内容、验证命令。输出执行计划到 `docs/superpowers/plans/`。 | 🚫 **不允许任何 TODO/TBD 占位符。** |

### 🔨 执行开发

| 技能 | 做什么 |
|------|--------|
| `executing-plans` | 按计划逐个执行任务，跟踪进度。遇到阻塞才停。 |
| `subagent-driven-development` ⭐ | **每个任务开一个新子代理**（独立上下文窗口），完成后经过两道审查门：① 是否符合设计？② 代码质量是否过关？不通过就打回重做。 |
| `dispatching-parallel-agents` | 自动识别互不依赖的任务，并行执行。每子代理在独立 Git worktree 中跑，互不冲突。 |

### ✅ 测试

| 技能 | 做什么 | 核心铁律 |
|------|--------|---------|
| `test-driven-development` ⭐ | **RED-GREEN-REFACTOR**：先写失败的测试 → 写最少代码让测试通过 → 重构。 | 🚫 **没有失败的测试，绝不写任何实现代码。** |
| `verification-before-completion` | 每次说"做好了"之前，**必须重新跑一次验证命令**，看实际输出和退出码。 | 🚫 **"理论上应该可以"不算数。** |

### 🐛 调试

| 技能 | 做什么 | 核心铁律 |
|------|--------|---------|
| `systematic-debugging` | 四阶段：① 收集日志和复现步骤（**不做任何修改**）→ ② 分析模式 → ③ 先写能复现 bug 的自动化测试 → ④ 修复。 | 🚫 **连续 3 次修复失败 → 触发架构审查。不允许乱试。** |

### 👀 代码审查

| 技能 | 做什么 |
|------|--------|
| `requesting-code-review` | 在任务完成、功能完成、合并前主动请求审查。用独立子代理逐文件审查。问题分 **Critical / Important / Minor** 三级。Critical 阻塞合并。 |
| `receiving-code-review` | 接受审查反馈：理解 → 验证 → 技术性反驳（如有证据）。不盲目接受，也不防御性拒绝。 |

### 🌲 分支管理

| 技能 | 做什么 |
|------|--------|
| `using-git-worktrees` | 在独立工作树中开发，不污染主分支。开发前先跑基线测试确保环境正常。 |
| `finishing-a-development-branch` | 收尾流程：确认已提交 → rebase → 跑全部测试 → 推送 → 合并/PR/保留/丢弃四选一。 |

### 🔌 扩展

| 技能 | 做什么 |
|------|--------|
| `writing-skills` | 元技能——教你（和 AI）怎么按 Superpowers 规范写新 skill。 |

## 一个完整流程示例

假设你说"帮我加一个用户登录功能"：

```
1. brainstorming
   我："这个系统现在有用户系统吗？用什么框架？需要支持哪些登录方式？
        我看了你的代码，建议两个方案：
        A. JWT token，无状态，适合前后端分离
        B. Session + Cookie，传统方案，简单但需要服务端存储
        你选哪个？"
   你："A"
   我：输出设计文档到 docs/superpowers/specs/2026-07-19-login-design.md

2. writing-plans
   我把设计拆成 8 个微任务：
   □ Task 1: 写 User model 的测试 → src/models/user.test.ts
   □ Task 2: 实现 User model → src/models/user.ts
   □ Task 3: 写 /login 路由的测试 → src/routes/auth.test.ts
   ...
   输出到 docs/superpowers/plans/2026-07-19-login-plan.md

3. subagent-driven-development
   对每个 Task 开一个独立子代理：
   Task 1 子代理：写测试 → 审查通过 ✓
   Task 2 子代理：写实现 → 审查不通过 ✗（缺了 bcrypt）→ 打回重做 → 通过 ✓
   ...

4. verification-before-completion
   全链路测试 → 确认通过 → 才说"好了"
```

## 总结：工程规范到底是什么

| 没有 Superpowers | 有 Superpowers |
|-----------------|---------------|
| 你说"加个登录"，直接写代码 | 先问清楚需求，给方案对比 |
| 写完了说"应该可以了" | 跑测试、看输出、确认无误 |
| bug 修不好就乱试 | 先找根因、先写复现测试、再修复 |
| 改着改着上下文崩了 | 每步保存，子代理隔离 |
| 从来没写过测试 | 没失败的测试就不写代码 |

**本质上就是把一个专业软件团队的开发流程，压缩成 AI 的行为规范。**
