## 对你有用的

| 子技能 | 嵌入式场景 | 举例 |
|--------|-----------|------|
| `brainstorming` | 你说"加个CAN通信"，它不会直接写代码，而是先问：波特率？标准帧还是扩展帧？用中断还是DMA？FIFO怎么分配？**问清楚了再动手**。 | ✅ 防止上来就写一堆用不上的代码 |
| `writing-plans` | 把一个功能拆成可执行步骤：配置引脚 → 初始化外设 → 写中断服务函数 → 测试回环。**不会跳步**。 | ✅ 嵌入式开发最怕漏配置 |
| `systematic-debugging` | UART 收不到数据？先不让你改代码，而是让你**先看时钟配置、查GPIO复用、查NVIC优先级**。三次修不好就触发架构审查。 | ✅ 硬件调试的根因分析法 |
| `verification-before-completion` | 说"PWM 配置好了"之前，必须先给你看**实际示波器截图或逻辑分析仪输出**。 | ✅ 不看波形就敢说配好了？ |
| `receiving-code-review` | 别人说你中断优先级设错了，它不会盲目接受，而是看参考手册验证。 | ✅ |

## 对你没用的

| 子技能 | 为什么没用 |
|--------|-----------|
| `test-driven-development` | 嵌入式 TDD 需要硬件在环或者仿真器，`stm32-mcp` 能做内存读写但跑不了单元测试框架。写一个测试比写功能代码还麻烦。 |
| `subagent-driven-development` | 嵌入式项目修改一个外设往往牵连时钟树、DMA、NVIC，子代理之间信息隔离反而容易出冲突。 |
| `using-git-worktrees` | 对纯软件项目有意义，但你的工程是 CubeIDE 项目，worktree 没有额外价值。 |
| `dispatching-parallel-agents` | 你不会同时改 TIM1 和 SPI2，因为它们在同一个 `.ioc` 文件里互相影响。 |

## 定论

```
Superpowers 对你有用的部分：规划 + 调试 + 验证
Superpowers 对你无用的部分：TDD + 子代理隔离 + worktree
```

**所以不需要装整个 Superpowers。** 你真正需要的是把这些嵌入式场景的纪律写进你的项目 `CLAUDE.md` 里，比如：

```markdown
## 规则
- 修改任何外设配置前，必须先列出受影响的时钟、引脚、DMA、中断
- 宣称功能完成前，必须提供实际的硬件验证结果
- 调试时先查根因（时钟→引脚→配置→逻辑），不要随机改代码
- CubeMX 生成的 USER CODE 区域不能触碰
- 所有外设初始化必须检查返回值
```
