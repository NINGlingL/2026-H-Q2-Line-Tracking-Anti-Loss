# 技术复盘

## 做成了什么

第二问循迹在第三天晚上完成稳定调参，最后版本结合八路寻迹、陀螺仪偏航角速度和单侧硬件编码器。视觉端也完整打通了“小球检测—坐标标定—滤波—串口发送—MSPM0 接收”的链路，且坐标精度和稳定性满足现场验证需要。

这些成果说明，独立模块验证是有效的；真正的问题出现在整车集成、机械进度和跨层故障定位。

## 关键失败原因

### 机械结构没有成为独立工作流

队伍没有机械成员，也没有固定的 CAD/3D 打印协作者。题目发布后，车辆、丝杆、水管槽、摄像头与滚球机构都是边做边调整，导致所有成员被机械任务占用，主控失去系统调试时间。

### PCB 路线没有及时止损

开源扩展 PCB 本身仍需大量焊接和分级验证。由于焊接经验与质量不足，多块板子做完后不能稳定使用，最终又切换到洞洞板。问题不是“没有工具”，而是缺少焊接流程、单级上电验证和明确的止损点。

### 软硬件问题混淆

第四天八路寻迹变得不准时，真实原因是电池电量不足造成电压下降，影响传感器稳定性。因为没有先记录八路原始值和带载电压，问题被当成软件丢线，最终代码增加了保持、偏航桥接、弧线搜索和超时停车等多层状态。

保护策略本身并非错误，但它们不应替代供电和传感器原始数据检查。

### 控制资源评估过晚

第三天才集中处理编码器资源限制，并尝试在高压时间窗口实现软件编码器，成本过高。类似限制应在题目拆解和引脚/定时器资源表阶段暴露，并尽早决定单编码器方案、外部计数方案或更换结构。

### 过度依赖 AI

不同模型对同一项目形成的上下文理解不同，频繁切换会造成架构漂移和重复解释。AI 生成代码如果缺少模块级验证、日志和回滚点，很容易把硬件问题包装成更复杂的软件问题。

更可靠的做法是固定一个主模型与一套项目文档；必须更换时，让更强的模型从题面、当前代码、接口表和已验证事实重新建立上下文，而不是盲目续写。

## 如果重来一次

1. 材料清单发布后完成标准模块采购和预验证，但不在题目发布前锁死最终结构。
2. 开题后先画整机装配草图、接口表和加工清单，再并行推进机械、电路、视觉、主控。
3. 第一天下午前确定机械负责人或外部 CAD/3D 打印协作渠道。
4. PCB 每焊完一个电源或接口区域就限流上电验证，连续失败后及时切换成熟模块或洞洞板。
5. 每个模块保留“输入—原始输出—通过标准—失败现象”的验证记录。
6. 整车异常严格按供电、接线、原始数据、驱动、控制算法分层定位。
7. 为第二问稳定版本设冻结点，后续试验从 Git 分支展开，不破坏可测版本。
